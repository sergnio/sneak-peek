Technical plan - Great Clips Web

A disposable, always-current Heroku app for every pull request

Selected model: a wildcard preview domain plus a dedicated GitHub Actions workflow that creates a named Heroku app per PR. This guarantees the final URL is configured before this Next.js app builds.

Target behavior

Open / reopen

Create

GitHub Actions creates a unique Heroku app, configures its hostname, and posts its URL on the pull request.

Every push

Update

The workflow rebuilds the same app from the latest PR head SHA. No manual deploy.

Close / merge

Destroy

The cleanup workflow removes the Heroku app, DNS record, and attached ephemeral resources.

Why this is the right fit

Heroku Review Apps handle the basic lifecycle natively, but this application requires a unique NEXT_PUBLIC_URL during its build for Auth0. The selected wildcard-domain model needs a deterministic app name and domain before building, so a dedicated GitHub Actions workflow is the robust implementation. It uses Heroku for the ephemeral runtime and GitHub for the PR lifecycle.

The repo already has a root Procfile, a heroku-postbuild script, and production-like Heroku deployment workflows. The current deploy script deliberately permits only great-clips-dev and great-clips-staging, so the preview workflow must be new and separate.

Lifecycle at a glance

Implementation plan

  1. Establish the preview boundary. Create a dedicated Heroku team/pipeline area and reserve a DNS namespace such as oci-preview.qa.greatclips.com. Each Heroku app receives its own DNS target, so the lifecycle workflow must create and delete the individual pr-<number> CNAME through the organization's DNS provider API. A wildcard Auth0 allowlist can cover those hostnames, but a single wildcard DNS record is not sufficient to route them to different Heroku apps. Keep great-clips-dev, great-clips-staging, and their deploy workflow unchanged.
  2. Use the existing Heroku entry points. No app.json is required for the selected custom workflow. The existing root Procfile starts yarn start:oci; heroku-postbuild builds the online-check-in workspace, so the current layout is compatible with buildpack deployment. Add app.json later only if the team switches to native Review Apps or needs declarative ephemeral add-ons.
  3. Provide config safely. Store non-secret preview defaults and secrets as GitHub environment variables/secrets, then apply them to each app from the workflow before build. Use preview/test API endpoints, never production credentials. Explicitly exclude local .env.local files from the deployment.
  4. Configure authentication and the dynamic URL. Define pr-<number>.preview.example.com as the URL scheme. Register the wildcard callback/logout URLs with Auth0, then set NEXT_PUBLIC_URL to that exact URL before build. This is required because Next.js embeds public variables into its client bundle.
  5. Add dedicated lifecycle workflows. On trusted pull_request open/synchronize/reopen, derive gci-web-pr-<number>, create/configure the app and custom domain if absent, read Heroku's DNS target, create the PR hostname CNAME through the DNS provider API, set preview config and build metadata, deploy the PR SHA, health-check it, and upsert one sticky preview comment. On pull_request.closed, delete the DNS record and destroy the named app. Use GitHub concurrency keyed by PR number to prevent stale releases. Use scoped Heroku and DNS service credentials stored as GitHub environment secrets.
  6. Run one rollout acceptance test, then automate the essentials. A single test PR must verify preview APIs, Auth0 login/logout, web-to-app encryption, an update at the same URL, and teardown. This is necessary because the workflow crosses GitHub, Heroku, DNS, Auth0, and Next.js build-time configuration. After sign-off, each PR only needs an automated health check; a scheduled orphan cleanup is a low-cost safety net for failed cleanup runs.

Important constraints

  • Auth0: callback and logout allowlists must accept the selected wildcard preview domain. Confirm the tenant's wildcard policy before implementation.
  • Next.js: NEXT_PUBLIC_* values are compiled into the client build. Changing them after release does not fix the deployed frontend.
  • Costs and limits: each open PR consumes a Heroku app, dyno, build minutes, and any add-ons. Set a budget alert and an automatic-review-app policy.
  • Data: previews must point at mock/QA services and use non-production keys. Do not inherit production config.

What not to do

  • Do not generalize .github/scripts/deploy-to-heroku.sh. It force-pushes to a shared app and has an explicit two-app allowlist.
  • Do not run previews from forked PRs with organization secrets. Restrict deployments to trusted, same-repository branches.
  • Do not use a long-lived personal API key. Create a dedicated Heroku service account or token with only the needed team/pipeline access, rotate it, and store it as a GitHub Actions secret.
